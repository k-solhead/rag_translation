# RAGによる前年踏襲翻訳（Streamlit）

翻訳作業において、前年（過去）と同じ文章や類似した表現をRAG（検索拡張生成：Retrieval-Augmented Generation）を活用して自動的に置き換えるアプリです。
**英→和（和訳）・和→英（英訳）の両方向**に対応しています。

従来の翻訳メモリ（TM: Translation Memory）の仕組みを、LLMとベクトル検索を使って高度化させたものです。

## 手順

1. idml2xlsxを使って英語と和文のIDMLファイルからテキスト情報を取り出して対訳表エクセルを作成
    - 対訳表には「文書情報」シート（案件名・ファイル名・顧客名・タグ・メモ）が付きます。ここに入力しておくと、登録時の初期値になります。
2. Docker Desktop（Windows）または Container Station（QNAP）で、DBとアプリをまとめて起動
    ```bash
    # 初回のみ：.env.example を .env にコピーし、POSTGRES_PASSWORD を英数字のパスワードに変更
    #           （同梱の .env には自動生成したパスワードが設定済み）
    docker compose up -d --build
    ```
    - DB（`tm-pg`）は初回起動時に `schema.sql` を自動実行してテーブルを作成します。
    - アプリ（`tm-app`）は DB の準備完了を待ってから起動します。
    - 状態確認：`docker compose ps` ／ ログ：`docker compose logs -f`
3. ブラウザで `http://localhost:8501`（NAS の場合は `http://<NASのIP>:8501`）を開く
4. 「データ取り込み」タブで対訳表エクセルをアップロードし、文書情報（案件名・ファイル名・顧客名・タグ・メモ）を確認・入力して「取り込む」ボタンで一括データベース化
    - 英文・和文の両方を一度にベクトル化して登録するため、1回の取り込みで英→和・和→英の両方の検索に使えます。
    - 1ファイル＝1文書。ファイル名（必須・一意）が登録済みの場合は「追加」か「置き換え」を選べます。
5. 「過去翻訳を検索」タブに英文または和文を貼り付け「検索」ボタンを押すと、一致度順に過去の原文とその訳文、入力文と過去の原文との差分が表示される
    - 検索の向きは自動判定（かな・漢字を含めば和→英）。手動で指定することもできます。
    - 「検索対象の絞り込み」で顧客名・案件名・タグを指定すると、該当する文書だけを対象に検索します。
6. 「翻訳」タブで Word / Excel ファイル（またはテキスト）を入力し、使う LLM を選んで「翻訳を実行」すると、前年の訳を踏襲した訳文を複数の LLM で作成し、Excel でダウンロードできる（詳細は下記「翻訳機能」）
7. 「用語集」タブで、顧客ごとの用語集（＋共通の用語集）を登録・編集できる
8. 「文書管理」タブで、登録済み文書の一覧の確認、文書情報の修正、文書の削除ができる

## 仕組み
- **文（文脈）の切り出し（Chunking）:** 前年と同じ文を見つけるため、段落ごとではなく、文章を「1文ごと（センテンス単位）」に分割。
- **ベクトル化（Embedding）:** 前年の英文・和文の両方をEmbeddingモデル（`multilingual-e5-small`=384次元・日英両対応）でベクトルデータに変換。
- **ベクトルDBへの格納:** 1行＝1組の対訳として、英文・和文それぞれの正規化文・ハッシュ・ベクトルをベクトルデータベース（PostgreSQL）に保存。検索の向きに応じて英文側・和文側の列を使い分けます。
- **検索ロジック** 意味的な「ベクトル類似」に加え、文字列同士の似ている度合い「トライグラム類似」、「完全一致」の３つの方法でハイブリッド検索。
- **差分表示** 検索順に表示し、それぞれ検索文との差分を表示します。英文は単語単位、和文は形態素解析（fugashi + unidic-lite）による単語単位で差分を取ります。
- **一致率** 英文は単語単位、和文は文字単位（空白・全角半角の違いは無視）で計算します。
- **文書の絞り込み** 顧客名・案件名・タグで対象文書を絞り込んだ場合、ベクトル検索は索引（HNSW）を使わず対象文書の全行と比較します（取りこぼし防止）。

## 翻訳機能（「翻訳」タブ）
RAG で抽出した前年の原文・差分・訳文を LLM に渡し、前年の訳を踏襲した訳文を作ります。

1. **入力**：Word（段落・表のセル）、Excel（全シートのセル）、または貼り付けたテキスト。既定では文単位に分けて処理します。
2. **過去訳の検索**：各文で過去訳を検索します。「過去訳（RAG）の検索対象」で前年の文書（顧客名・案件名など）に絞ると精度が上がります。
3. **一致率による処理の振り分け**（しきい値は「詳細設定」で変更可）

    | 一致率 | 処理 | 内容 |
    |---|---|---|
    | 100% | 前年訳流用 | LLM に送らず前年の訳文をそのまま使う（費用ゼロ） |
    | 75〜99% | 修正 | 前年の訳文と「変更点の一覧」を渡し、差分の箇所だけ直させる |
    | 40〜74% | 参考 | 過去の類似訳（最大3件）を用語・文体の参考として渡し、新しく訳させる |
    | 40%未満 | 新規 | 用語集だけを渡して新しく訳させる |

4. **用語集**：選んだ顧客の用語集＋共通の用語集から、その文に含まれる用語だけをプロンプトに入れます。
5. **複数の LLM を並列実行**し、結果を Excel（「翻訳結果」「実行条件」「使用した用語」の3シート）にまとめます。差分は色付き（削除＝赤の取り消し線、追加＝緑の太字）、行は処理ごとに色分けされます。
6. **自動チェック**：数値の不一致、用語集の訳語の未使用、訳し残しの可能性を「チェック」列に表示します（あくまで目安です。「1億円」→「100 million yen」のような単位換算も数値差異として表示されます）。

### 使える LLM（プロンプトの形式はモデル名から自動判定）
| 表示 | 対象 | プロンプト |
|---|---|---|
| RAG | LM Studio / Ollama の一般的なモデル（gemma など）、Claude、OpenAI、Gemini | 前年訳・差分・用語集を使うプロンプト（`translation.py` の `SYSTEM_PROMPT`） |
| 従来プロンプト | `fine_tuned_*` | translate と同じ短いプロンプト（用語集はシステムプロンプトに追加）。RAG プロンプトでも選べます |
| PLaMo翻訳 | `plamo-2-translate` | テキスト補完 API で `<\|plamo:op\|>` 形式。修正は前年の対訳を3回、参考は類似の対訳を few-shot として渡す |
| TranslateGemma | `translategemma-*` | テキスト補完 API で Gemma のターン形式。修正は前年訳のポストエディットを指示し、参考は類似の対訳を few-shot として渡す |

PLaMo翻訳・TranslateGemma は差分の一覧を渡さず、前年の原文と今年の原文を並べて反映させます。用語集は使いません。従来プロンプトは前年訳・差分を使いません（前年訳流用の判定は共通です）。

### 設定（`.env`）
| 変数 | 内容 |
|---|---|
| `LMSTUDIO_BASE_URL` | LM Studio の接続先（既定 `http://192.168.11.83:1234/v1`） |
| `LMSTUDIO_CONCURRENCY` | LM Studio への同時リクエスト数（既定 1。GPU に余裕があれば増やす） |
| `OLLAMA_BASE_URL` | Ollama の接続先（既定 `http://192.168.11.83:11434`。空なら Ollama は使いません） |
| `OLLAMA_CONCURRENCY` | Ollama への同時リクエスト数（既定 1） |
| `OLLAMA_NUM_CTX` | Ollama のコンテキスト長（既定 8192。Ollama 側の既定のままだと RAG プロンプトが切り詰められます） |
| `ANTHROPIC_API_KEY` | Claude API のキー。空なら Claude は選択肢に出ません |
| `CLAUDE_MODELS` | 選択肢に出す Claude のモデル（既定 `claude-haiku-5-5,claude-sonnet-5-5`） |
| `CLAUDE_CONCURRENCY` | Claude API への同時リクエスト数（既定 4） |
| `OPENAI_API_KEY` | OpenAI API のキー。空なら OpenAI は選択肢に出ません |
| `OPENAI_MODELS` | 選択肢に出す OpenAI のモデル（既定 `gpt-6-luna,gpt-6.1-sol`） |
| `OPENAI_CONCURRENCY` | OpenAI API への同時リクエスト数（既定 4） |
| `GEMINI_API_KEY` | Gemini API のキー。空なら Gemini は選択肢に出ません |
| `GEMINI_MODELS` | 選択肢に出す Gemini のモデル（既定 `gemini-3.8-flash`） |
| `GEMINI_CONCURRENCY` | Gemini API への同時リクエスト数（既定 4） |
| `OPENAI_REASONING_EFFORT` / `GEMINI_REASONING_EFFORT` | 任意。推論の深さ（例 `low`）。空なら各社の既定。翻訳では `low` にすると速く安くなります |
| `OPENAI_TEMPERATURE` / `GEMINI_TEMPERATURE` | 任意。temperature を受け付けないモデルがあるため、空なら送りません |
| `CLOUD_MAX_TOKENS` | OpenAI / Gemini の出力トークン上限（既定 8192）。推論型モデルは推論にもトークンを使うため多めにしています。「出力が空でした（finish_reason=length）」と出たら増やしてください |

`.env` を変更したら `docker compose up -d` で反映されます（再ビルド不要）。

### Claude（Teamプラン）を API で使う手順
1. Team の Owner が claude.ai の「Organization settings > Billing」の「API credits」で、Claude Console（platform.claude.com）の組織を紐付ける（Standard シート 1人 月20ドル、Premium シート 1人 月100ドル、チーム合計で月500ドルまでのクレジット。月末で失効）
2. Claude Console で API キーを発行し、`.env` の `ANTHROPIC_API_KEY` に設定
3. 使いすぎ防止のため、Console で翻訳用のワークスペースを作り、月の利用上限を設定しておくと安心です

クレジットを使い切ると API は止まります（プラン料金に上乗せはされません）。システムプロンプトはキャッシュされ、完全一致の文は LLM に送らないため、費用を抑えられます。

### OpenAI・Gemini を API で使う手順
- **OpenAI**：platform.openai.com で API キーを発行し、`.env` の `OPENAI_API_KEY` に設定します。API の料金は ChatGPT の契約とは別の従量課金です。
- **Gemini**：Google AI Studio（aistudio.google.com）で API キーを発行し、`.env` の `GEMINI_API_KEY` に設定します。Google 公式の OpenAI 互換エンドポイント（`https://generativelanguage.googleapis.com/v1beta/openai/`）経由で呼び出します。
  - **無料枠のキーでは、送った内容が Google のサービス改善に使われます。** 顧客の原稿を送るため、課金を有効にした有料枠のキーを使ってください（有料枠では使われません）。
- モデル名は各社で随時更新されます。使いたいモデルは `OPENAI_MODELS` / `GEMINI_MODELS` で指定してください。
- OpenAI・Gemini は「翻訳」タブと、用語集タブの「LLM で文中の用語を抽出」の両方で選べます。

## トークン数管理（「トークン数管理」タブ）
OpenAI・Claude・Gemini を呼び出すたびに、応答の `usage` に含まれるトークン数を加算し、プロバイダーごとの累計を表示します（「翻訳」と、用語集の「LLM で文中の用語を抽出」が対象。LM Studio / Ollama は対象外）。

| 表示 | Claude | OpenAI / Gemini |
|---|---|---|
| 入力トークン（キャッシュ以外） | `input_tokens` | `prompt_tokens` − キャッシュ分 |
| 出力トークン | `output_tokens` | `completion_tokens`（推論分を含む） |
| キャッシュ入力トークン（読み込み） | `cache_read_input_tokens` | `prompt_tokens_details.cached_tokens` |
| キャッシュ出力トークン（書き込み） | `cache_creation_input_tokens` | 応答に項目がある場合のみ（無ければ 0） |

- 累計はデータベース（`token_usage` テーブル）に保存するため、再起動しても消えず、アプリを使う全員の使用分が合算されます。テーブルはアプリ起動時に自動で作られます。
- 各プロバイダーの「ゼロに初期化」で、そのプロバイダーの累計を 0 に戻せます（確認のチェックを入れてから押します）。「集計開始」はゼロに戻した日時です。
- 4 つの値にそれぞれの単価（入力・出力・キャッシュ読み込み・キャッシュ書き込み）を掛けて足すと、おおよその料金になります。
- 記録に失敗しても翻訳は止まりません（ログに警告が出ます）。

## 用語集（「用語集」タブ）
- 「（共通）」と顧客ごとの用語集を管理します。顧客名は文書の顧客名から選ぶか、新しく入力します。
- 翻訳時は「共通」＋「選んだ顧客」の用語集を使い、同じ英語の用語は顧客の訳語を優先します。
- **区分（必須／参考）**
  - 必須：固有名詞・製品名・取り組み名など、毎回この訳語を使う用語。プロンプトの `<glossary>` に入れ、自動チェック（用語未使用）の対象にします。
  - 参考：文脈で訳し分ける一般的な語（例：Asahi Group →「アサヒグループ」／「当社グループ」）。プロンプトの `<glossary_reference>` に「文脈に合えば使う」として入れ、チェックの対象にしません。従来プロンプトのモデルには必須の用語だけを渡します。
- **用語集を編集**：表で直接、追加・修正・削除（「必須」のチェックで区分を切り替え）して「保存」。Excel でダウンロードもできます。
- **ファイルから取り込む**：CSV / Excel。列名 `en` / `ja`（英語・日本語、英文・和文も可）、任意で `note`（備考）・`区分`（必須／参考）。
  - 列名のない2列のファイル（1列目＝英語、2列目＝日本語）もそのまま読めます（日本語が1列目なら自動で入れ替え）。
  - 用語全体を囲む「」『』“” は既定で外し、同じ組は1つにまとめます（例：「ISO14001」→ ISO14001）。
  - `採用` 列がある場合（用語抽出の候補一覧）は、○ の行だけを取り込みます。

### 対訳表から用語を抽出
「用語集」タブで「対訳表から用語を抽出」を選びます。対訳は、登録済みの文書（顧客名・案件名などで絞り込み可）か、対訳表ファイル（idml2xlsx の出力など）から取ります。

| 抽出方法 | 内容 |
|---|---|
| 短い対訳 | 見出し・表の項目など短い対訳（既定：英語4語以下・2回以上出現）をそのまま候補にします。LLM 不要 |
| LLM | 文の対訳を30組ずつ LLM に渡し、固有名詞・取り組み名・指標・専門用語・略語を抜き出させます。和文に訳語が見当たらない候補（LLM の思い違い）は自動で除きます |

- 各候補について、対訳全体での **文中の出現**（英文に用語が出てくる数）と **一貫性**（そのうち和文に訳語が使われている割合）を出し、既存の用語集と照合して「新規／登録済み／訳語が違う」を付けます。
- 「既存の用語の一貫性も表示する」をオンにすると、登録済みの用語も一貫性付きで表示されます。一貫性の低い用語は「参考」に変える目安になります（「登録済み」の行を採用すると区分だけを更新）。
- 候補は画面で「採用」「区分」を直して取り込むか、Excel でダウンロードして確認後、「ファイルから取り込む」で取り込めます。
- 初期値：採用＝新規で一貫性80%以上かつ2回以上出現、区分＝略語・固有名詞・取り組み名など、または一貫性の高い複数語の用語を「必須」。
- 用語集テーブル（`glossary_terms`）と区分の列はアプリ起動時に自動で作られるため、既存の DB を作り直す必要はありません。

## データベース構成（`schema.sql`）
| テーブル | 主な列 |
|---|---|
| documents（文書） | `doc_key`＝ファイル名（一意）、`title`＝案件名、`client`＝顧客名、`tags`＝タグ（配列）、`note`＝メモ |
| segments（対訳） | `document_id`、`seq_no`、`page_ja` / `page_en`、`en_text` / `en_norm` / `en_hash` / `en_embedding`、`ja_text` / `ja_norm` / `ja_hash` / `ja_embedding` |
| token_usage（トークン数の累計） | `provider`、`input_tokens`、`output_tokens`、`cache_read_tokens`、`cache_write_tokens`、`requests`、`updated_at`、`reset_at` |
| glossary_terms（用語集） | `client`＝顧客名（空＝共通）、`en`、`ja`、`note`、`required`＝必須（true）／参考（false） |

対訳表（Excel）の列は `日本語` / `英語`（idml2xlsx の出力そのまま）のほか、`ja_text` / `en_text`、旧形式の `target_ja` / `source_en` も読み込めます。

## 特長
- 従来の「翻訳メモリ（TM）」と違い、「完全に同じではないけれど、少しだけ単語が変わった文章」に対しても、前年のトーンを維持したまま柔軟に翻訳できる

## 今後の開発方針
- 採用した訳文（翻訳後に修正したもの）を翻訳メモリに登録し直し、翌年の「前年訳」として使えるようにする。
- 大量の文書を急がず翻訳する場合に、Claude の Message Batches API（料金半額）を使う。


## Docker 運用メモ
| 操作 | コマンド |
|---|---|
| 停止 | `docker compose down` |
| コード変更後の再起動 | `docker compose up -d --build` |
| DB を初期化してやり直す（**データ全削除**） | `docker compose down -v` |
| psql で DB に入る | `docker compose exec db psql -U tm -d tm` |
| 対訳表を CLI で一括投入 | `docker compose cp 対訳表.xlsx app:/tmp/data.xlsx` → `docker compose exec app python ingest.py /tmp/data.xlsx --defer-index`（文書情報は `--doc-key` `--title` `--client` `--tags` `--note` でも指定可。`--replace` で既存の対訳を置き換え） |

- 以前 `docker run` で作った `tm-pg` コンテナが残っていると名前が重なるため、先に `docker rm -f tm-pg` で削除してください。
- 埋め込みモデル（multilingual-e5-small）はビルド時にイメージへ同梱されるため、起動後はインターネット接続不要です。初回ビルドは数分〜十数分かかります。
- DB のポートは同じPC内（127.0.0.1）からのみ接続できます。アプリ画面（8501）は社内LANに公開されるため、ルーターでポート開放しないでください。

## 旧バージョン（英→和のみ）からの更新
テーブル構成が変わったため、**データベースを作り直して対訳表を登録し直してください**（既存データは削除されます）。
```bash
docker compose down -v
docker compose up -d --build
```
その後、「データ取り込み」タブから対訳表を登録し直します。
